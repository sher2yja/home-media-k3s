# Разработка

## Что это

Домашний медиасервер в двух формах развёртывания:

- **стенд** — `kubeadm` на трёх libvirt/KVM-машинах одного ноутбука. Здесь всё
  разрабатывается и проверяется живьём;
- **k3s** — одна нода на компьютере пользователя. Это то, что уезжает в релиз.

Общая часть манифестов у них одна (`k8s/media-stack/`), различия вынесены в
оверлей kustomize (`deploy/k3s/`). Порты, пути и человеческие названия сервисов
живут в единственном месте — `app/config.py`, и CI сверяет с ним собранные
манифесты.

## Запуск из исходников

Зависимостей у приложения нет: интерфейс на `tkinter`, HTTP-клиенты на `urllib`.
Виртуальное окружение не нужно, нужен только Python 3.12 и Tk.

```bash
sudo apt install python3-tk        # Debian/Ubuntu: tkinter отдельным пакетом
python3 app/main.py
```

## Проверки

Тестового фреймворка в проекте нет намеренно. Проверяемая логика собрана в
самопроверках, каждая — один запускаемый файл:

```bash
cd app && python3 media.py      # разбор очередей *arr и статусов Jellyseerr
cd app && python3 install.py    # шаблон томов, пункт меню, перенос со ссылками,
                                # ожидание узла (kubectl и sleep подменены)
cd app && python3 wire.py       # подстановка полей в схему настроек, разбор причины отказа
cd app && python3 icon.py       # кодирование PNG без сторонних библиотек
cd app && python3 guides.py     # состав подвкладок и подстановка портов из config
```

Сами запросы к API Sonarr, Radarr и Prowlarr здесь не подделываются: разъедется
как раз то, что подделано. Их проверяет job `e2e` на живом кластере.

Всё остальное проверяется теми же командами, что в CI:

```bash
ruff check app && python3 -m compileall -q app
python3 -c "import yaml,sys; list(yaml.safe_load_all(open(sys.argv[1])))" ФАЙЛ.yaml
kubectl kustomize deploy/k3s                    # оверлей собирается
for f in infra/vms/scripts/*.sh; do bash -n "$f"; done && shellcheck infra/vms/scripts/*.sh
```

Многодокументные YAML требуют `safe_load_all`, а не `safe_load`.

## Что приложение делает под капотом

Установка ставит стек только на Linux, и ветвлений по ОС в `app/` нет ни одного.
Путь через WSL2 для Windows снят 2026-08-30: проверить его было нечем. Единственный
шов, куда он вернётся, — `install.ensure_cluster()`.

```
ensure_desktop_entry  пункт меню + иконка PNG (см. ниже, почему обязательно)
prepare_dirs          создать папки от имени пользователя (не от root: контейнеры
                      linuxserver.io работают под PUID=1000 и иначе не запишут)
ensure_cluster        pkexec env INSTALL_K3S_EXEC=... sh k3s-install.sh
wait_for_node         дождаться появления Node, потом condition=Ready
create_secret         пароль торрента: генерация + PBKDF2, kubectl create secret
apply_volumes         hostpath-volumes.yaml.tmpl с подставленными путями
apply_stack           kubectl apply -k deploy/k3s
apply_monitoring      профиль «полный»: kubectl apply -k deploy/k3s/monitoring
apply_identity        PUID/PGID по os.getuid() того, кто запустил установщик
wait_for_pods         kubectl wait --for=condition=Ready pod --all
wire.configure        FlareSolverr в Prowlarr и метки на индексерах, папка для
                      скачивания в торренте, торрент и корневые папки
                      в *arr, hardlink'и, Prowlarr → Sonarr/Radarr
```

**`wait_for_node` ждёт в два шага, и это не перестраховка.** `kubectl wait --all` по
ресурсу, которого ещё НЕТ, не ждёт вовсе — он мгновенно выходит с `no matching resources
found`. Сразу после `systemd: Starting k3s` объект Node как раз не зарегистрирован.
Одношаговая проверка превращала обычную медлительность машины в «Кластер не пришёл в
готовность» через доли секунды после успешно поставленного k3s — сообщение, по которому
человеку нечего делать. Проявлялось это только случайными падениями `e2e`: 30.08 упало на
коммите, который этого кода не касался вовсе (между стартом k3s и вызовом прошло 8
секунд, узел не успел). Теперь сначала опрос `get nodes` до появления узла, потом
`condition=Ready` на остаток времени. Самопроверка `install.py` подменяет `kubectl` и
`time.sleep` и проходит оба исхода, включая тот, где узла нет вовсе.


Отдельный бинарь `kubectl` не ставится: k3s несёт его в себе (`k3s kubectl`), а
kustomize встроен в сам kubectl.

## Ключевые решения

**Тома — статические hostPath, а не local-path.** Провижинер k3s кладёт данные в
`/var/lib/rancher/k3s/storage/<uuid>/`. Для медиатеки это сразу неверно: папка с
фильмами должна лежать там, где её видно. Для конфигов это ломает ещё и само
приложение — `media.py` читает ключи API прямо из `<config_dir>/<сервис>/config.xml`.
Поэтому оверлей проставляет всем заявкам пустой `storageClassName`, а тома
генерируются при установке с `claimRef` на конкретную заявку.

**У четырёх сервисов `/data` смонтирован в БУКВАЛЬНО одинаковый путь.** Это не
стиль, а условие работы hardlink'ов: Sonarr и Radarr делают на импорте жёсткую
ссылку вместо копии, только если видят файл по тому же пути на той же файловой
системе. Иначе каждый фильм занимает место дважды, молча.

**Пароль qBittorrent считается в одном месте** — `app/install.py`. Скрипт стенда
`infra/vms/scripts/08-qbittorrent-secret.sh` вызывает те же функции. Две копии
PBKDF2 — способ однажды тихо разъехаться и получить «неверный пароль» без
объяснений.

**PUID берётся у того, кто запустил установщик, а не из манифеста.** В манифестах
стенда стоит 1000 — владелец домашней папки на типовой машине. Но папки создаёт
установщик от своего имени, и на машине со вторым аккаунтом контейнер писать в
них не сможет. Sonarr отвечает на это `400` при добавлении корневой папки, не
называя причиной права: отладить такое, не зная заранее, почти нельзя. Поэтому
`apply_identity` проставляет `PUID`/`PGID` после `apply`, а CI сверяет список
развёртываний с `PUID` в манифестах со списком в `install.py`.

**Настройки сервисов берутся из их же `/schema`, а не выдумываются.** У \*arr набор
полей у настроек меняется между версиями. Захардкоженный словарь однажды разъедется
с сервисом и даст отказ, в котором не будет ни слова о причине. `wire.py` просит
у сервиса готовый шаблон нужной реализации и подменяет в нём несколько значений.
Причина отказа, если он всё-таки случится, достаётся из тела ответа: «сервис
ответил 400» чинить нельзя, «Folder is not writable by user abc» — можно.

**Смена папок переносит данные, сохраняя жёсткие ссылки.** `shutil.move` через
границу файловых систем разрывает hardlink: файл под двумя именами превращается
в два файла, и медиатека тихо занимает вдвое больше. `install.migrate` строит
карту inode и восстанавливает связи через `os.link`, а исходник удаляет только
после полностью удавшегося копирования — не хватило места, всё возвращается назад.

**Торренту отдельно говорят, куда складывать.** По умолчанию qBittorrent
сохраняет в свой `/config/Downloads` — то есть на том с настройками, а не на том
с медиатекой. Отказ от этого молчаливый и дорогой: том с настройками маленький,
но хуже то, что жёсткая ссылка через границу томов невозможна, и \*arr на импорте
делают копию. Каждый фильм занимает место дважды, ошибки при этом нет ни одной —
а ведь ровно ради совпадения томов `downloads` и `library` и лежат рядом. Путь
выставляет `wire.set_download_dir()` через API торрента (идемпотентно, чинит и уже
работающую установку) и засевает initContainer в манифесте — на свежей установке
он верен с первой секунды. Совпадение обоих мест с `config.DOWNLOADS_DIR`
сверяет CI. Найдено живым прогоном: Sonarr и Radarr сами сообщали об этом в
`/api/v3/health`, а установщик считал, что всё хорошо.

**Проверка Cloudflare обходится седьмым сервисом, а не подбором заголовков.**
Крупные трекеры отдают программе не страницу, а задачу на JavaScript
(`cf-mitigated: challenge`), и Prowlarr получает `403`. Подделывать User-Agent
бессмысленно — задачу надо выполнить, а не назваться браузером. FlareSolverr
держит внутри headless-браузер: решает задачу и отдаёт куки. Он единственный в
стеке без тома (хранить нечего) и единственный `ClusterIP` (наружу не смотрит,
с ним разговаривает только Prowlarr). Прописывает его `wire.add_flaresolverr()`
вместе с меткой `flaresolverr`.

**Метка нужна с обеих сторон, и это выяснено измерением, а не вычитано.** Сначала
прокси создавался без меток — в расчёте на то, что «без тегов значит для всех».
Проверка показала обратное, и первая же попытка исправить оказалась только
половиной ответа: метку поставили на прокси, а индексер оставили без неё, потому
что тот опыт был испорчен — вместе с прокси метился и тестовый индексер. Три
состояния на живом Prowlarr:

```
прокси с меткой, индексер без   -> 403 за 2.2 с, FlareSolverr не тронут
прокси с меткой, индексер с ней -> 200, в логах «Challenge solved!»
прокси без метки, индексер без  -> 403 за 2.1 с, FlareSolverr не тронут
```

Метка на прокси отвечает не за «включён», а за «к каким индексерам применять»:
прокси без меток не применяется ни к одному. Отсюда два следствия в коде.
`add_flaresolverr()` не только создаёт прокси, но и **чинит** уже созданный без
метки — такой выглядит настроенным и молча не работает. А `tag_indexers()`
помечает сами индексеры; больше установщику сделать нечего, потому что индексеры
человек добавляет уже после установки. Кнопка «Связать сервисы» и есть способ
пометить только что добавленный сайт — так это и описано в `MANUAL.md`.

`tag_indexers()` сохраняет с `?forceSave=true`, и это не мелочь: обычный `PUT`
заставляет Prowlarr заново сходить на сайт и проверить индексер — тридцать секунд
против пяти в `media.TIMEOUT`. Запрос отваливается по таймауту, хотя метка при
этом успевает сохраниться: молчаливое «не сработало», которого не видно в ответе.
С `forceSave` — `202` за десятые доли секунды.

Оба пути проверяются в `e2e` шагом «Обход Cloudflare чинится сам»: у прокси
снимается метка и проверяется, что она вернулась, а для индексеров заводится
заглушка на `Torznab` с адресом `http://127.0.0.1:1` — она создаётся мгновенно и
в сеть не ходит, поэтому проверяется метка, а не работа трекера.

Порт живёт в `config.FLARESOLVERR_PORT`, и CI сверяет его с манифестом так же,
как сверяет NodePort'ы остальных.

**Логин и пароль торрента — латиница, и это измерение, а не вкусовщина.** С
кириллическим логином или паролем qBittorrent пароль меняет и сам пускает
(проверено своим клиентом и curl'ом из пода Sonarr), а Sonarr с Radarr получают
от него `401` на `/api/v2/app/webapiVersion` и отвечают «Unable to connect to
qBittorrent». Человек сменил бы пароль, убедился бы, что вход работает, — и
заказы перестали бы скачиваться без единой заметной ошибки. Обе половины
проверены по отдельности: кириллический логин с латинским паролем ломает так же.
ASCII-спецсимволы (`&`, `=`, `%`, `$`, `#`) проходят нормально. Правило держит
`wire.check_credentials()`, у него своя самопроверка.

**Смена пароля трогает три места, и пропуск любого ломает скачивание молча.**
`install.change_qbittorrent_credentials()`: сам qBittorrent через его API,
Secret в кластере и download client в Sonarr и Radarr. Secret обновляется
`kubectl patch --type=merge` со `stringData` — не `delete+create` (между ними под
не нашёл бы Secret и не стартовал) и не через временный файл (это пароль).
Через API, а не пересозданием Secret'а, потому что конфиг засевается
initContainer'ом только когда файла ещё нет: на работающей установке новый Secret
не изменил бы ничего, и это выглядело бы как удавшаяся смена.

**Полный профиль не работал ни разу, и молча.** Два независимых дефекта, оба
нашлись только при живом прогоне, оба без единой ошибки в выводе:

1. `nodeSelector: kubernetes.io/hostname: k8s-worker01` в `10-prometheus.yaml` и
   `30-grafana.yaml` — узел СТЕНДА. У пользователя такого узла нет, поды вставали
   в `Pending` навсегда. Медиастек от этого защищён патчем в `deploy/k3s`, а
   мониторинг применялся мимо kustomize — и в том же файле стояло, что он «на k3s
   работает как есть». Теперь у мониторинга свой оверлей,
   `deploy/k3s/monitoring`, с тем же патчем.
2. `nodePort: 30300` у Grafana оказался занят Traefik'ом, который k3s ставит сам и
   берёт под него два СЛУЧАЙНЫХ порта из диапазона NodePort. Service не
   создавался, `apply` возвращал код 1 — а `install()` присваивал этот код в
   `result`, от которого зависело, дойдёт ли дело до связывания сервисов. То есть
   занятый порт под графики оставлял медиасервер несвязанным. Порт сменён на
   30030, занятость проверяется до установки, а неудача мониторинга больше не
   влияет на остальное: добавка не должна отменять главное.

Гарантии от второго дефекта не давал ни один номер порта — Traefik брал свои
случайно. Поэтому лечение было не в номере, а в предпроверке. **С 30.08 лечение
радикальнее: Traefik просто не ставится** — `--disable=traefik` в `K3S_EXEC`.
Ingress'ов в проекте нет ни одного, все сервисы выведены через NodePort, и
обслуживал он ровно ничего, занимая при этом два порта и 34 МиБ. `e2e` поднимает
кластер флагами из `install.K3S_EXEC`, а не своей строкой, и проверяет, что
Traefik не развернулся, а NodePort'ов ровно шесть.

Предпроверка портов при этом осталась: на кластерах, поднятых раньше, Traefik
никуда не делся, да и занять порт может любая программа. Заодно у неё нашлась
своя дыра. «Свой это порт или чужой» она выясняла через `media.service_status()`,
а тот берёт список сервисов из **профиля в состоянии**. Стоит человеку выбрать
простой профиль и на вопрос «удалить графики?» ответить «оставить» — Grafana
работает, в состоянии её нет, и предпроверка советует остановить постороннюю
программу на 30030, показывая на его же Grafana. Теперь `_ports_check` спрашивает
кластер (`monitoring_installed()` плюс живой ответ самой Grafana) — тот же
принцип, что уже был записан в docstring `monitoring_installed()`.

**Дашборд провижинится, а не рисуется руками.** Grafana со свежим томом встречает
пустой страницей: datasource есть, панелей нет. Человек, включивший полный профиль
ради графиков, не видит ни одного. `40-dashboard.yaml` кладёт восемь панелей, а
кнопка в окне ведёт не на главную Grafana, а сразу на дашборд —
`config.grafana_dashboard_url()`. UID закреплён (`home-media`) и сверяется в CI:
на неизвестный UID Grafana отвечает не ошибкой, а страницей «Dashboard not found»,
то есть сломанная кнопка выглядела бы рабочей. `uid: prometheus` у datasource —
из той же породы: без него Grafana выдаёт случайный, и панели молча пустые.

**Ключи API нигде не спрашиваются у пользователя.** \*arr держат их в своих
`config.xml`, Jellyseerr — в `settings.json`, оба каталога на этой же машине.
Просить человека найти и скопировать ключ — ровно то, ради устранения чего
писалось приложение.

**Иконка рисуется кодом и обязана быть файлом на диске.** GNOME Shell 46 больше
не берёт картинку из свойства окна `_NET_WM_ICON`: окну, которому не нашлось
`.desktop`, он рисует заглушку `application-x-executable` — серую шестерёнку без
имени. Поэтому `install.ensure_desktop_entry()` кладёт PNG в
`~/.local/share/icons` и `.desktop` со `StartupWMClass`, совпадающим с классом
окна. Пиксели и PNG-кодировщик — в `app/icon.py`, полсотни строк на stdlib
вместо Pillow в зависимостях. Имя класса живёт в одном месте
(`install.DESKTOP_ID`), `ui.WM_CLASS_NAME` берётся оттуда: разъедутся — окно
потеряет и имя, и иконку, а понять почему будет неоткуда.

**Долгие операции не выполняются в потоке окна.** Установка идёт минуты, опрос
шести сервисов — до тридцати секунд. Всё это уходит в отдельный поток, результат
возвращается через очередь, которую разбирает `after()`. К виджетам обращается
только поток окна, как требует Tk.

## Когда провайдер не отдаёт адрес сайта

Prowlarr отказывается добавить индексер: `Name does not resolve (сайт:443)`. При
этом сайт открывается в браузере на той же машине, а повторные попытки
срабатывают через раз. Медиасервер здесь ни при чём, и в его настройках причины
нет.

**Что происходит.** CoreDNS в k3s пересылает всё, что не про кластер, на серверы
из `resolv.conf` ноды:

```
forward . /etc/resolv.conf     ->  192.168.3.1, 1.1.1.1, 1.0.0.1
cache 30
```

Первый в списке — домашний роутер, и он отвечает `SERVFAIL` **избирательно**: на
`github.com` даёт нормальный ответ, на домен трекера — отказ. CoreDNS выбирает
сервер из списка случайно, поэтому имя разрешается через раз, а отрицательный
ответ ещё и живёт 30 секунд в кэше. Отсюда и ощущение плавающей поломки.

Браузер на том же хосте при этом работает: `systemd-resolved` устроен иначе и
берёт первый успешный ответ, а не случайный сервер.

**Как убедиться, что дело в этом:**

```bash
dig @192.168.3.1 rutracker.org   # роутер:   status: SERVFAIL
dig @1.1.1.1     rutracker.org   # публичный: status: NOERROR + адреса
dig @192.168.3.1 github.com      # контроль:  status: NOERROR — фильтрация выборочная
```

**Лечение — отдельный резолвер для нужных зон.** k3s импортирует в Corefile
`/etc/coredns/custom/*.server`, а туда монтируется опциональный ConfigMap
`coredns-custom`. Блок для конкретной зоны перекрывает общий `.:53`, всё
остальное — включая имена внутри кластера — продолжает резолвиться как раньше:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns-custom
  namespace: kube-system
data:
  trackers.server: |
    rutracker.org:53 {
        errors
        cache 30
        forward . 1.1.1.1 1.0.0.1
    }
```

`kubectl apply -f` — и всё. Перезапускать CoreDNS не нужно, плагин `reload`
подхватывает изменение сам; kubelet доносит ConfigMap до тома до минуты.

**Как проверить, что подхватилось.** Образ CoreDNS без оболочки, `exec` в него не
войдёт, поэтому смотрим логи: до правки там `No files matching import glob
pattern: /etc/coredns/custom/*.server`, после `Reloading complete` это
предупреждение остаётся только про `*.override`. Дальше — тридцать запросов
подряд из любого пода:

```bash
kubectl -n kube-system logs deploy/coredns --tail=8
kubectl exec -n media deploy/prowlarr -- sh -c \
  'for i in $(seq 1 30); do nslookup ИМЯ >/dev/null 2>&1 || echo провал; done; echo готово'
```

**Почему не правим `resolv.conf` хоста.** Это поменяло бы разрешение имён для всей
машины, включая браузер и всё остальное, ради одного домена в одном приложении.
Блок в CoreDNS ограничен и кластером, и перечисленными зонами.

**Почему приложение не чинит это само.** Поймать избирательную фильтрацию заранее
нельзя: роутер отвечает отказом ровно на те домены, которые фильтрует, а на
контрольный запрос отвечает нормально. Поэтому `install._dns_check()` не
диагностирует, а называет: показывает, у кого кластер спрашивает адреса. Человеку,
упёршемуся в `Name does not resolve`, строка с адресом его роутера экономит вечер
поисков в настройках Prowlarr, где причины нет.

## Сборка

Собирает конвейер, локально — только чтобы посмотреть:

```bash
pip install pyinstaller==6.22.2
pyinstaller --clean --noconfirm home-media-k3s.spec
```

В бандл кладутся оба каталога манифестов: `deploy/k3s/kustomization.yaml`
ссылается на `../../k8s/media-stack` относительным путём, и внутри распакованного
бандла этот путь обязан разрешаться.

## Конвейер

| Задача | Когда | Что делает |
|---|---|---|
| `check` | всегда | линтер, самопроверки, YAML, bash+shellcheck, сборка оверлея, сверка портов с манифестами и с текстами, запрет на вернувшиеся слова и захардкоженный логин, правила показа кнопки на графики, сборка окна под xvfb |
| `e2e` | `master` и теги | ставит настоящий k3s флагами из `install.K3S_EXEC`, гоняет `install.install()` — тот же код, что у пользователя, — опрашивает сервисы через `media.service_status()`, проверяет, что Traefik не развернулся, и меняет логин с паролем торрента во всех трёх местах |
| `build` | всегда | PyInstaller, артефакт `home-media-k3s-linux` |
| `release` | теги `v*` | выкладывает артефакты `build` в GitHub Release без пересборки |

## Что не проверено

**Windows.** Версия под него не выпускается. Путь через WSL2 был написан по
документации и не запускался ни разу — ни `wsl --install`, ни повышение прав
через UAC, ни продолжение установки после перезагрузки. Проверить его было нечем,
поэтому 2026-08-30 он снят из кода целиком; снятое лежит в теге `v0.1.3`.

**Чистая машина.** `e2e` в CI — самое близкое к ней, но это раннер GitHub, а не
компьютер человека с его правами, окружением и уже занятыми портами.
